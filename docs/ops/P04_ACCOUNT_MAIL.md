# P04 account mail: encrypted outbox and explicit worker

This is source for review. P04 does not enable password registration, install a scheduler, read an email secret or send a real message. The existing verified sender/key remains unchanged. P05 supplies the `/verify-email` and `/reset-password` browser forms; mail links carry the bearer value in `#token=`, never a query string. Never open registration until that complete journey and release gates pass.

## Transaction and secret boundaries

The password service calls `ensure_capacity` before account eligibility lookup and calls `enqueue` in the same transaction as the digest-only verification/reset challenge. Both known and unknown accounts meet the same capacity/configuration gate. Failure rolls back the challenge and job together. The database job contains an address digest and AES-256-GCM ciphertext, with a fresh 96-bit nonce; the recipient, subject and link are encrypted. Associated data binds the job UUID, purpose, recipient digest and precise UTC expiry. It cannot be moved to another job, recipient or purpose. Only a worker decrypts the message in the ordinary implementation. Hashes, passwords, provider secrets and Google credentials are never mail fields.

The **separate** `ACCOUNT_MAIL_OUTBOX_KEY` is 32 random bytes encoded with padded URL-safe base64. It is independent of the session secret, database passwords and Resend key. The web process needs that encryption key; symmetric encryption means a compromised web process with it could also decrypt pending mail. This protects tokens in a database-only leak; it is not protection after application/key compromise. Use owner-only private secret files outside the shared project. Do not place values in Git, browser assets, logs, screenshots or command arguments.

The worker needs the same outbox key, enabled private application-storage settings and a Resend **Sending-access** key restricted to `account.aqua-ai.us`. Only the worker receives `RESEND_API_KEY`. The previously approved private mail-secret location is `/home/ben2004/.aqua-runtime/mail/.env`; keep its permissions and do not print its content. No helper here discovers or consumes that live file automatically. The worker uses the application runtime role, a one-connection bounded pool and the private PostgreSQL socket. That role can access application tables: this phase does not claim a mail-only database role, tenant RLS or stronger isolation from a compromised worker. No analytical database/model/Google credentials are required by the worker.

## Delivery bounds and failure handling

### Recipient anti-spam and fixed content

The follow-up review adds one pending/sending logical message per canonical mailbox and verification/reset purpose, a five-minute cooldown, and at most three newly queued jobs in any rolling 24 hours for that mailbox/purpose. Independent history survives deleted challenge/mail jobs and worker restart; it retains at most three timestamps per key, 4,096 keys total and cleans up at most 64 expired keys at a time without evicting active allowances. Repeated requests receive the same generic acknowledgement and retain the original valid proof. Retries are the same logical job and remain constrained by the separate delivery-attempt budgets. Mailbox aliases are not merged; the conservative global caps still apply. Keep spent recipient histories when fencing a restore, as with the existing delivery counters.

Verification cannot consume a reset quota or suppress a successful-reset notice. A public notice is queued only by a completed reset; failed proof creates none. Subjects/body/link paths come from fixed templates. Enqueue checks exact challenge purpose, canonical mailbox, digest, expiry and current reset epoch; selection checks still-valid proof/account binding; the worker decrypts and validates the entire canonical template before any transport call. Invalid content is never sent. The server-configured canonical origin must contain no controls, backslashes, credentials or extra path/query/fragment; request headers and submitted URLs cannot choose it. See [the follow-up security review](../implementation/P04_SECURITY_REVIEW.md) for attack evidence and remaining limitations.

Run the packaged `python -m auth.mailworker` entrypoint explicitly with a reviewed worker-only environment. It attempts **at most one job**, prints only `attempted`, `idle` or a fixed `unavailable` status, and exits. `ops/accountmail/worker.env.example` lists variable names with both flags disabled. There is no automatic thread in the API and no scheduler installed by this change. A later reviewed scheduler can invoke this at one-second or slower intervals; adding processes does not multiply the persisted global lease or volume budget.

The queue retains at most **4,096 rows**, with **2,048 pending/sending** partitioned into at most 1,024 verification, 768 reset and 256 password-change-notice jobs. Registration cannot consume recovery/security queue slots. The same purpose-specific capacity check runs before account eligibility lookup, preserving generic outcomes under saturation. Admission uses one short advisory lock and deletes at most 64 expired rows per transaction. Counting retained rows is `O(Q)` with a hard `Q <= 4096`; there is no claim of an unbounded constant-time count. Due/expiry/challenge indexes support bounded selection and cleanup. Successful, permanent/invalid, exhausted and expired jobs immediately overwrite ciphertext with a nondecryptable tombstone; consumed challenges remove their linked jobs transactionally. Ciphertext is at most 4 KiB per pending job (about 16 MiB at maximum retained jobs, plus row/index overhead). Tokens/messages expire within 24 hours; purpose-specific challenge expiry may be shorter.

Claims commit before the external request. One persisted **90-second lease** permits one delivery in flight across workers; a random lease UUID fences completion from a stale worker. Delivery admission permits at most **one attempt/second, 20 attempts/hour and 60 attempts/day**, regardless of account, cookie, source or worker restart. Hourly delivery partitions are **5 verification / 5 reset / 10 password-change notice**, and daily partitions are **20 per purpose** (summing to the global ceilings). The worker selects password-change notices first, resets second and verification last through purpose/due indexes. A registration backlog or exhausted verification allowance therefore cannot make recovery wait behind registration or spend its reserved quota. Unused purpose allocations are deliberately not lent to other purposes. A reset flood can still exhaust the small reset allocation; account/address/global issuance limits, monitoring and P12 capacity review remain necessary. These conservative product ceilings reserve headroom; they do not assert provider-plan capacity or P12 performance results. Each HTTP attempt spends a delivery allowance, including a retry. Exhausted budgets do no provider work and normal admission resumes when the stored window expires.

The adapter sends plain text only to the fixed HTTPS Resend endpoint, from the fixed verified sender. It follows no redirects, trusts no proxy environment, retries nowhere internally, bounds connections/accepted body/time (16 KiB response accounting plus a bounded transport read buffer; elapsed checks between reads with five-second read timeouts), and never emits response bodies or provider exception text. Provider 429/5xx and unknown acceptance use the **same job UUID, request body and Idempotency-Key**, at most three total attempts. Backoff is 30 then 60 seconds. Reclaims cannot restart attempts; retries stop within **23 hours** of the first attempt and before message/challenge expiry. Resend documents a 24-hour idempotency retention window, so a retry never intentionally crosses it. Do not change sender/body for a pending job or manually replay it under a new key after unknown acceptance. A key rotation keeps the outbox key until jobs are drained, or deliberately cancels old pending jobs and requires new user requests; replacing the key silently makes old envelopes undecryptable.

A successful provider response means **accepted**, not delivered to an inbox. Failed, consumed, expired and corrupt challenges/messages cannot produce valid new authentication. Logs contain only fixed outcome categories. A provider outage, failed database completion or worker crash preserves leases/retry counts and does not trigger unbounded retries. A job still in flight at process death may be reclaimed after its lease using the same idempotency key. No exactly-once delivery guarantee is claimed beyond those provider and lifetime boundaries.

## Review and recovery

Before activation, migrate schema 3 explicitly, verify both link forms and their token handling/no-referrer policy, review the worker-only environment without displaying secrets, confirm sender status/account limits, run a separately approved real delivery smoke test, and review scheduler/monitoring. This source alone enables none of these live operations. Monitor aggregate queue states/attempt counts and fixed outcome events; alert on repeated failures and near-capacity without recording recipient addresses or bearer links. Disable the worker flag to contain delivery while preserving pending rows; disable password issuance independently while retaining working Google login/session revocation.

For recovery use a forward fix or maintenance mode, retaining migration/checksum history and grant/revocation state. Backups can include encrypted pending jobs: keep the outbox key recoverable independently and constrain restores so already sent jobs are not recreated as new UUIDs. Do not restore old challenges/sessions into active authentication without the separately required revocation/epoch fencing. A provider outage does not justify dumping the outbox/key or extending expired bearer tokens.

Unit/integration tests capture synthetic mail in memory and replace HTTP with a fake. They cover encrypted recipient/token storage, AAD substitution, corrupt envelopes, transaction rollback, capacity, registration-flood versus recovery/notice fairness, volume/inflight budgets, lease loss/reclaim, expiry/consumption, stable retries, idempotency headers, fixed logs and HTTP failure recovery. See P04 phase evidence for executed results; this runbook does not imply any live message was sent.
