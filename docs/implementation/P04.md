## Result and account boundaries

Registration initially requests a mailbox proof without reserving an account or accepting a preselected password. A single-use verification token and a freshly chosen password create the canonical account transactionally. This prevents pre-registration with an attacker-chosen password. Duplicate email/identity races cannot silently merge users; Google-only accounts cannot acquire a password through reset. Explicit add/link/change/unlink methods remain P10 work. Google login and existing durable session checks remain available independently.

Password login creates the same opaque, revocable session contract as Google: canonical `user.id`, safe profile, CSRF, current dataset access and boolean capabilities. It rechecks current account state, epoch, credential and session capacity after detached hashing; no database connection remains leased during Argon2 work. Registration creates no analytical dataset grant. A signed-in account without a grant remains unable to query.

Verification/reset bearer tokens are random, digest-only challenges with expiry and transactional one-use consumption. Verification defaults to 24 hours; reset to 30 minutes. Reset checks the current verified email, existing password credential and issue-time epoch; it replaces the credential, advances the epoch, revokes current sessions and consumes outstanding reset challenges atomically. The transaction queues a password-change notice and removes consumed challenge mail. Verification and reset return 204 without automatic login; reset clears the caller's old session cookie.

Mail requests return one generic 202 acknowledgement for eligible, existing and unsupported mailbox states. Eligibility does not change the configuration/capacity preflight, durable admission or public acknowledgement. Generic accepted email work has a minimum 50 ms duration; any padding occurs after its database lease is released; this is bounded mitigation, not a claim of indistinguishable production timing. Invalid input, stale proof, overload and unavailable services have fixed errors without submitted values. Private responses remain no-store.

## API and activation controls

All new endpoints are under `/api/v1/auth`. Obtain a fresh `GET /bootstrap?action=...` challenge for each attempt. Supported actions are `registration`, `verification`, `login`, `reset-request` and `reset`. The action-bound CSRF token, matching Origin and opaque password-action cookie are required for the corresponding POST; consumption commits before work and the proof cannot be replayed for another action.

| Endpoint | Body / successful result |
| --- | --- |
| `POST /registrations` | `{email}`; generic 202 acknowledgement |
| `POST /email-verifications` | `{token,password}`; 204; fresh login required |
| `POST /password-login` | `{email,password}`; existing canonical auth/session response |
| `POST /password-reset-requests` | `{email}`; same generic 202 acknowledgement |
| `POST /password-resets` | `{token,password}`; 204; old sessions invalidated |

`PASSWORD_AUTH_ENABLED`, `PASSWORD_REGISTRATION_ENABLED` and `PASSWORD_RECOVERY_ENABLED` default to `false`. Pausing registration or new recovery requests need not disable existing password login/session validation. Google configuration is separate. The mail integration and explicit worker have their own disabled flags. Missing/corrupt corpus, storage, hash resources or mail configuration fails closed with fixed diagnostics; valid password login does not require working email delivery.

P05 supplies the password UI, `/verify-email` and `/reset-password` forms, fragment extraction/clearing, password-manager behavior and full browser journeys. This phase does not advertise those pages as finished. Activation requires the [password cutover procedure](../ops/P04_PASSWORD_CUTOVER.md) and [account-mail runbook](../ops/P04_ACCOUNT_MAIL.md).

## Password policy and bounded work

Email policy supports validated ASCII mailbox syntax with a case-insensitive key. It preserves dots and plus suffixes and does not guess that aliases identify the same person. Internationalized mailboxes remain unsupported until one compatible normalization/provider policy is implemented. Passwords use NFC consistently, 15–128 code points and at most 512 UTF-8 bytes; controls/surrogates and common passwords are rejected at establishment. Passwords are never trimmed or truncated, and no uppercase/digit/symbol mixture or external password-check API is required. Establishment also rejects passwords containing fewer than three distinct characters.

Argon2id policy version 1 uses **19 MiB, two iterations, one lane**, 16-byte salt and 32-byte output. Encoded hash costs/alphabet are checked before invoking Argon2 so corrupt database content cannot request arbitrary memory. Unsupported/absent/disabled credentials perform bounded dummy verification. Only reviewed cost tuples are accepted; future changes require tested policy/version updates and rehash-on-success compatibility. Request hashing is limited to two shared durable slots plus a two-slot local semaphore. This bounds active request-hash memory at about 38 MiB plus implementation/process overhead; it is not an overall service memory or throughput claim.

| Shared control | Default |
| --- | --- |
| Password login | 10 per peer, 30 globally, 5 per normalized address / 60 seconds |
| Verification/reset email requests | 5 per peer, 30 globally, 3 per address / 60 seconds; shared operation budget |
| Proof consumption | 10 per peer, 30 globally / 60 seconds |
| Pending mailbox challenges | At most 3 active per email/purpose; 4,096 retained password challenges; batched expiry cleanup |
| Admission rows | 2,048; expiry cleanup in batches of 64; no live-budget eviction |
| Request hashing | At most 2 global jobs; no DB lease during hash computation |
| Edge limits | Separate 5/minute password-login, registration and recovery zones; verification/reset proof zone 5/minute; bootstrap shares the bounded login-bootstrap zone |

Socket-peer limits remain aggregate behind the tunnel. Anonymous bootstrap budgets are shared across Google/password actions, so registration-bootstrap floods can temporarily return 429 to legitimate login/recovery bootstraps until cooldown. The verified separation covers POST/mail allocations, not end-to-end availability. Forwarding headers/cookies cannot choose a new quota identity; trusted per-visitor attribution is separate ingress work. Login, mail, proof, account and global limits complement each other. Hash slots deliberately have no timer: a paused worker may still own Argon2 memory. A crash fails closed until the operator stops **all** auth workers and clears only proven retired slots. See the recovery runbook; never auto-expire or periodically delete live slots.

The common-password corpus is an MIT-licensed, pinned SecLists subset: **10,898** unique NFC/casefold SHA-256 digests from the one-million-password source, filtered to the supported policy bounds. The runtime ships the digest file, provenance and license; it never downloads a corpus or submits a password online. The file is exactly 708,370 bytes with SHA-256 `a5b8b74b66c0ed54d90098285cb0dbe02217ae41d7c91f0c57cf4a761e14521a`. Its bytes/entry count are checked fail-closed. `.gitattributes` forces LF for the integrity-checked file; Docker explicitly packages its assets. This subset is not every compromised password; provenance-preserving updates and dependency/advisory review remain maintenance work.

## Mail, complexity and recovery

The encrypted outbox commits with the challenge. It stores no plaintext address, link or token. A separate 32-byte AEAD key protects database-only exposure; the symmetric web key is not protection against application compromise. Only the separate worker receives the restricted Resend secret. Delivery uses stable job/body/idempotency, a single fenced lease, fixed volume/attempt/expiry bounds and immediate terminal bearer purge. Reserved queue and hourly/daily purpose allocations prevent anonymous registration from consuming recovery/security delivery capacity. Details and limitations are in the [mail runbook](../ops/P04_ACCOUNT_MAIL.md); no real email is sent by these tests.

Email/token/account lookups use indexed equality and bounded joins. Session creation retains P03's covering live-session seek, `O(log n + session cap)`. Admission and queue counts are `O(K)`/`O(Q)` with explicit hard caps, not claimed unbounded constant-time work. Cleanup is batched; mail selection performs at most three indexed purpose/due seeks. Argon2 intentionally spends bounded memory/time. P12 supplies representative throughput, latency/fairness and capacity evidence; limits alone are not those measurements.

Additive `0003_password_auth.sql` adds password challenge provenance, shared admission/hash slots and encrypted outbox/control tables. Immutable `0001` and `0002` remain unchanged. Explicit migration is required before schema-3 code starts; web startup never migrates. A schema-2 image is not a compatible rollback after this migration. Keep flags off while diagnosing, use a reviewed schema-compatible forward fix or maintenance, and preserve durable revocation. Restore to a separate private DB with all workers detached; fence epochs/sessions/challenges, clear retired hash slots and cancel/wipe restored pending mail before reconnecting. Never let a restore replay mail or revive recovery links.

The pre-merge review adds one pending job, a five-minute cooldown and three new logical messages per rolling 24 hours for each mailbox/verification-or-reset purpose.
