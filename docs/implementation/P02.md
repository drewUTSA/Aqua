## Result and compatibility

P02 supplies the private PostgreSQL identity-storage foundation, independently
from the hosted analytical dataset. Initial tables cover users/emails, external
identities, password-hash records, sessions, authentication challenges, dataset
grants and preferences. Constraints enforce valid state, digest sizes, unique
identities, one primary email and challenge/session owner consistency. No default
dataset grants or public signup are created.

The dedicated PostgreSQL process has no TCP listener or container network.
The DB and explicit backend/migration jobs share a socket volume; application
mounts are read-only and require SCRAM credentials. Data uses its own persistent
volume. Owner, migrator, runtime and backup roles have separate privileges and
connection caps. Credentials stay in owner-only AQUA runtime folders outside the
shared checkout. The installer refuses existing resources/roles and preserves
data on partial failure rather than resetting it.

New `storage/` configuration cannot fall back to analytical credentials or select
an arbitrary host/database/role. Each web process defaults to four connections,
eight waiting callers and a two-second acquisition timeout, with validated hard
ceilings. SQL/lock deadlines apply to each transaction. Failed and successful
leases discard session state before reuse; prepared statements are disabled to
make those resets reliable. Driver failures are fixed diagnostics/category logs.

Explicit migrations use canonical checksums, a ledger and transaction advisory
lock. They serialize concurrent operators, reject changed/unknown history, roll
back interrupted work, and never execute on web startup. The web role cannot
own schema objects, create roles, run DDL or change migration history.

`GET /api/ready` is a new **internal loopback diagnostic**. With storage disabled
it reports that state; enabled storage requires schema version 1, otherwise it
returns fixed 503. Nginx rejects the route and normalized aliases without
contacting the backend. `/api/health` stays dependency-free. Existing Google
authentication and all current query/response shapes are unchanged.

Production Python now uses the same hashed dependency graph as CI, with a pinned
base and strict Docker context/COPY allowlists. Psycopg Pool 3.3.3 is the only
added runtime dependency. This prevents the parser dependency drift caught
during the P01 release. Frontend Docker tag/digest maintenance remains later
release work; P02 changes only its readiness routing, not the React interface.

## Complexity and budgets

Identity/email/token uniqueness and owner-based session/grant lookups use B-tree
indexes: typically `O(log n + k)` for a bounded returned page and `O(log n)` index
maintenance, not a blanket constant-time promise. The active-session index starts
with owner and includes a stable ID; P03 must pair indexed reads with atomic
locking/caps. No application login/chat query is added prematurely. Preferences
are bounded to 64 KiB at the database boundary; parsing/validation is linear in
that bounded payload. Ledger checking is linear in migration count plus actual
DDL cost. Connection/waiting limits bound concurrent work independently of those
query costs. P12 must measure representative query plans and throughput before
raising worker counts or claiming production capacity.

## Operations, migration and rollback checkpoint

Follow [ops/appdb/README.md](../../ops/appdb/README.md) for exact installation,
attachment/activation, restricted encrypted off-server collection, non-destructive
restore drill and rollback commands. Preserve both volumes on rollback; never
drop accounts/session data to undo a code change. Real exports must go directly
to encrypted backup storage, never to chat or build output. Independent recovery
password storage is already user-confirmed; no repeat password/setup prompt is
required. Backup collection is not scheduled or run against real data here.

The final narrow server snapshot confirms P01 source at 07055eb, both services
healthy, no fixed P02 container/data/socket volume, 32 logical CPUs, approximately
29.5 billion bytes available RAM and 41.0 billion bytes project filesystem space.
Only the pre-existing `.env.bak` remains untracked. Snapshots are not reservations
or peak-load measurements, and project free space does not prove Docker capacity.
