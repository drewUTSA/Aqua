# P03 — canonical identity and revocable Google sessions

**Status: implementation and isolated verification; not deployed.** P02 remains
live at `5ac90fcca45a6a74bab5d6f792388c05804d87a2`, with private storage ready at
schema 1. P03's final matrix and release evidence must be recorded before its
PR/cutover checkpoint is approved. No commit or push is performed by the agent.

## Result

Google's verified issuer/subject resolves to a canonical internal UUID. Concurrent
first logins serialize on that identity and database uniqueness; an email
collision with another account is rejected rather than silently linking methods.
Google issuer, audience, expiry, nonce and verified-email rules remain enforced.
Only a safe profile is returned to the browser: `user.id`, `email`, `name` and
`picture`. A Google subject is not fabricated for that contract.

Session cookies contain new random opaque `v2` tokens. The app DB stores token
and CSRF digests, account epoch, activity/expiry and revocation state. Protected
requests check current account state, epoch, expiry and current durable dataset
grant. A copied cookie fails after committed revocation or an account epoch/state
change. Logout does not return success or delete the cookie until its durable
revocation transaction succeeds. DB failure denies protected operations.

An authenticated account without a current dataset grant remains signed in but
cannot query. Existing explicit approvals may seed an absent grant only after
fresh Google verification, with matching provider identity and recorded subject
or authoritative-email provenance. Current configuration and the durable grant
are both checked; a revoked grant is never silently recreated by logging in.
Grant version and account epoch participate in the private cache scope.

Google challenges are durably single-use and bound to the browser's login cookie,
Origin, CSRF and provider nonce. Consumption commits before provider verification;
a failed callback must obtain a new challenge. No DB connection or admission
lock is held during the Google network call. General session validation and
logout remain usable when Google configuration is unavailable.

The frontend validates canonical UUIDs and keys private workspace state by that
ID. During unresolved or failed logout, it retains the same private drafts and
results in a hidden, inert workspace and offers a retry. Confirmed logout/401 or
an account change removes that state and aborts requests. Late old-account
responses cannot enter the replacement workspace. A confirmed 401 clears state
even if the subsequent login-configuration request fails.

Secure/HttpOnly/SameSite cookies, HTTPS `__Host-` binding, exact Origin checks,
CSRF protections and private no-store responses remain in force. Malformed
request responses omit submitted credential values and private diagnostics.

## Budgets and costs

| Control | Default / behavior |
| --- | --- |
| Active sessions | 5 per canonical account; atomic account lock and rejection at the cap, rather than silent eviction |
| Idle / absolute lifetime | 1,800 / 3,600 seconds; absolute expiry never slides; ordinary GET polling does not renew idle lifetime |
| Login challenge | 600 seconds; single-use even when a callback fails |
| Challenge issuance | 10 per socket peer and 60 globally per 60-second window |
| Google callbacks | 10 per socket peer and 30 globally per 60-second window, before verification |
| Verified account login | 5 per canonical account per 60-second window, shared across sessions/workers |
| Admission storage | At most 2,048 keys; expiry/record cleanup in batches of 64; no eviction of a live enforced budget |
| DB work | Existing P02 connection/waiter limits and transaction deadlines remain enforced |

Admission counters live in PostgreSQL and survive worker replacement. A short
transaction lock serializes bounded counter bookkeeping. Forged forwarding
headers or cookies do not create a new trusted peer. The current tunnel/proxy
topology makes that peer an aggregate budget, not a reliable per-person IP;
trusted client-IP attribution needs its own ingress review.

Token/identity/grant reads use B-tree lookups, normally `O(log n)` plus fixed join
work. A covering `(user_id, auth_epoch, idle_expires_at)` index seeks live sessions
and returns at most the configured cap: `O(log n + cap)`. Account locking makes
cap enforcement atomic under concurrent logins. Admission scans are bounded by
the key cap; cleanup limits deletion work to the batch. These are algorithm and
resource bounds, not production throughput measurements. Session limits and
login budgets do **not** replace P07's account/global AI job admission.

## Migration, checkpoint and later work

`0001_identity.sql` remains immutable. Additive
`0002_identity_policy.sql` adds identity observation/provenance fields, grant
version advancement, bounded durable admission records and session/challenge
indexes. Explicit migration reaches schema 2; web startup never migrates.
Production rollout requires the reviewed new migrator image **before** starting
P03 code, and storage must remain enabled through the existing socket overlay.

Every legacy signed profile cookie is deliberately rejected. Existing users must
sign in again; their old cookie is never accepted through a fallback path.
Pause for PR and cutover review, then follow
[the identity cutover runbook](../ops/P03_IDENTITY_CUTOVER.md). Once durable
sessions are activated, rollback must retain revocation guarantees: use a
compatible durable-session release or a forward fix/maintenance state, not P02's
stateless authentication. Preserve data, migration history and credentials.

P04 supplies password registration/login, verification and recovery. P07 supplies
shared AI job/concurrency admission and stream revalidation. P09 supplies saved
preferences; P10 supplies session-management/linking UI; P12 supplies measured
capacity and final launch verification. P03 is not a claim that those features,
full customization, production penetration testing or real backup recovery are
complete. The hosted analytical DB and its connection/bootstrap code remain
outside this change.
