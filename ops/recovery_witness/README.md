# Independent retirement witness

This Windows operator component records every signed retirement checkpoint before a witnessed Aqua publisher can acknowledge its sequence in PostgreSQL. Use a computer and account under separate custody from the database host. Keep the witness available whenever Aqua must acknowledge a closure.

## Enroll a forward installation

1. Stop the old publishers and restrict their database credentials. Establish the current installation ID, identity-key ID, key commitment, checkpoint verification key and signed genesis through the installation ceremony. Enrolling a historical backup as current would give an incorrect recovery point. An existing installation needs independent continuity evidence through its current head before switching to witnessed publication.
2. On the recovery PC use an owner-only directory outside the repository, for example `%LOCALAPPDATA%\Aqua\Recovery\witness\<installation-id>\`. Put the four public values in `profile.json` using the keys `installation_id`, `identity_key_id`, `key_commitment` and `public_key`. Record the exact file SHA-256 independently. Keep encrypted backups and the journal under separate recovery procedures. An administrator able to rewind the entire witness disk can also rewind its journal.
3. Provision distinct Ed25519 identities for the service generation and station. The Aqua service keeps its 32-byte generation key in `host/publication.key`, with the existing host-file ownership and permissions. The Windows station uses a CurrentUser DPAPI-protected 32-byte Ed25519 seed in `%LOCALAPPDATA%\Aqua\RecoveryIdentities\witness-<installation-id>.dpapi`. Exchange public pins through the installation ceremony. Keep both private identities separate from the checkpoint signer and from exported archives.
4. Run `receive.py --profile <path> --profile-sha256 <pin> enroll --service-public-key <hex>` with only the signed 208-byte genesis on binary stdin. Enrollment creates a new journal exclusively. A missing journal or incomplete enrollment requires custody review.
5. Add a `witness` object to `host.json` containing `generation`, `service_public_key` and `witness_public_key`. Use version 2 of the installed publisher profile with `witness_sha256` set to `retirement_host.witness_profile_pin(settings)`. Record the new installed-profile hash in the release configuration. The pinned installation and generation must match before the host can open a signer or database. Retire older launch profiles and credentials during activation.
6. Start `station.py` with the pinned public profile, generation, both public keys and an explicit loopback port. Use a private transport under operator custody to connect Windows loopback to a UID 1000, mode 0600 Unix socket named `witness.sock` in the host publisher's mode 0700 private directory. The existing publisher container sees this directory read-only and stays network-isolated. The station listener serves signed append requests only. The key exchange and tunnel are deployment-specific.

Each request has a 32-byte fresh challenge, credential generation, signed checkpoint and service signature. The receiver pins the publisher key for that generation, validates the checkpoint and its predecessor, commits it durably, then signs the exact request hash. The host verifies that signature before SQL acknowledgement. If the channel fails, the same stored checkpoint can be retried using a fresh challenge. Old challenges and credentials cannot authorize a later generation.

## Recover after both databases are lost

1. Stop application writers, any old publisher and mail senders. Keep the replacement isolated from public traffic. Fence the current generation on the recovery PC using `receive.py ... fence --generation <number> --fence-id <uuid>`. Preserve the returned record for the operator log. Reopen the independent journal on every attempt with the same fence ID.
2. Decrypt the separately held application and authority backups using their designated recovery identities. Use `recover.recovery_archive(...)` with the independent witness, active generation, fence ID, authority bytes, and independently selected runtime and schema pins. Keep its context open through restore, SQL verification and reconciliation. It verifies the protected head, source pins, signing keys and complete chain against the live fence.
3. Restore both databases into an empty, offline replacement. Use the existing six-table authority SQL verifier. With all writers stopped, initialize a fresh correctly owned checkpoint inode with the verified bytes. Run the isolated `append_provision.py --execute --device ... --inode ... --restored-records ... --chain-sha256 ...` setter and require its exit, readback and signed-chain validation. Keep that file read-only for application and recovery roles.
4. Run the existing restore-session fence before reconciling with the dedicated recovery role. Use `recovery_driver.reconcile_exact` with the frozen chain digest and the real mail-worker lifetime lock. Verify all events, sealed fingerprints and application retirement mirrors. Keep maintenance in force for a staging manifest, stale data, wrong key, failed purge, interrupted operation or missing account history. Check ordinary startup against the repaired app and verify that unrelated data is intact.
5. Keep the station fenced while the operator verifies the replacement and confirms old writers are gone. An explicit `Witness.release` requires the exact fenced cut and a previously unused public key for the next service generation. Requalify its version-2 publisher profile and private tunnel before admitting a new writer. The public app and station listener cannot lift this fence.

The legacy app-only operator continues to cover retained-authority recovery. The independent path requires the external journal plus operator-controlled target isolation, trusted custody and backup availability. Deployment and retention must be qualified on the actual service and recovery station.
