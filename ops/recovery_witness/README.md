# Independent retirement witness

This Windows operator component records every signed retirement checkpoint before a witnessed Aqua publisher can acknowledge its sequence in PostgreSQL. Use a computer and account under separate custody from the database host. Keep the witness available whenever Aqua must acknowledge a closure.

## Enroll a forward installation

1. Stop the old publishers and restrict their database credentials. Establish the current installation ID, identity-key ID, key commitment, checkpoint verification key and signed genesis through the installation ceremony. Enrolling a historical backup as current would give an incorrect recovery point. An existing installation needs independent continuity evidence through its current head before switching to witnessed publication.
2. Prepare the four public values for `profile.json` using the keys `installation_id`, `identity_key_id`, `key_commitment` and `public_key`. Record its exact file SHA-256 independently. Reserve the path `%LOCALAPPDATA%\Aqua\Recovery\witness\<installation-id>\` for step 5. Keep encrypted backups and the journal under separate recovery procedures. An administrator able to rewind the entire witness disk can also rewind its journal.
3. Before creating the per-installation witness directory, run `forward_station.py --installation <new-installation-uuid> --execute` on the Windows recovery PC. The prepared owner-only identity vault must have only the current operator and SYSTEM with inherited full-control rights for its files. This one-shot command writes a new CurrentUser DPAPI-protected Ed25519 seed to `%LOCALAPPDATA%\Aqua\RecoveryIdentities\witness-<installation-id>.dpapi`, verifies it through DPAPI and emits its public pin. Preserve the pin through an independent channel. Keep archive credentials and checkpoint signing material separate.
4. On the installed source, stage the reviewed operator package and the public enrollment envelopes described below. Hold public writers, mail senders and scheduled publishers in maintenance. Run `forward_controller.py prepare --execute --envelope-sha256 <pin>`. It reacquires the normal maintenance locks, verifies the physical signed genesis and the current database head, creates the separate owner directory `host/forward-v1/` and emits a new service public key and the signed genesis. Its helper mounts the legacy host and publisher configs read-only, the checkpoint read-only, the PostgreSQL socket read-only and the new directory read-write. The legacy checkpoint signing key is outside those mounts. Existing enrollment and any prior authoritative event close this path. An interrupted first creation must be inspected before another attempt.
5. Create the per-installation operator-owned Windows witness directory and its four-field public profile, verifying the returned genesis SHA-256 against the installation ceremony. Run `receive.py --profile <path> --profile-sha256 <pin> enroll --service-public-key <hex>` with that exact 208-byte record on **binary** stdin. Then start `station.py` with the public profile and its SHA-256, generation 1, both public keys and an explicit loopback port. Provide a private transport between Windows loopback and `host/forward-v1/witness.sock` on the source. The source socket must be UID 1000, mode 0600 in the mode 0700 forward directory. The station listener accepts authenticated append requests only.
6. Run `forward_controller.py activate --execute --envelope-sha256 <activation-pin>` with the new service public key added to the activation envelope. The source checks the exact fresh genesis again, submits a fresh signed challenge to the station, verifies the station signature, and then writes `host/forward-v1/host-v2.json` and `host/forward-v1/publisher-v2.json` exclusively. An exact retry verifies and reuses the completed files. Store the returned publisher profile SHA-256 in the release configuration. The presence of the forward directory blocks the original version-1 publisher. The source helper, by design, never starts application writers or a publisher.

Stage the reviewed `forward_controller.py` and `forward_source.py` beside the installed Linux `install.py` and `installation-sources.json`. Verify the SHA-256 of both added files against the selected source revision before use. The fixed source enrollment files are `operator/forward-prepare.json` and `operator/forward-activate.json` in the designated installation root. The installer-derived public data supplies `installation_id`, `identity_key_id`, `key_commitment`, checkpoint `public_key`, `genesis_sha256`, reviewed `runtime_image`, `source_sha256`, maintenance `plan_sha256` and `legacy_profile_sha256`. Add the independently confirmed `witness_public_key` and reviewed `helper_sha256` of `forward_source.py`. The activation file also pins `service_public_key`. Keep the exact byte hash of each envelope separately. Every source action verifies the installed operator manifest and actual stopped-writer state. Forward enrollment only applies to a genuinely new installation whose genesis was independently established before any service was made available. Historical recovery needs its actual original custody, trustworthy current head and archives.

Each request has a 32-byte fresh challenge, credential generation, signed checkpoint and service signature. The receiver pins the publisher key for that generation, validates the checkpoint and its predecessor, commits it durably, then signs the exact request hash. The host verifies that signature before SQL acknowledgement. If the channel fails, the same stored checkpoint can be retried using a fresh challenge. Old challenges and credentials cannot authorize a later generation.

## Recover after both databases are lost

1. Stop application writers, any old publisher and mail senders. Keep the replacement isolated from public traffic. Fence the current generation on the recovery PC using `receive.py ... fence --generation <number> --fence-id <uuid>`. Preserve the returned record for the operator log. Reopen the independent journal on every attempt with the same fence ID.
2. Decrypt the separately held application and authority backups using their designated recovery identities. Use `recover.recovery_archive(...)` with the independent witness, active generation, fence ID, authority bytes, and independently selected runtime and schema pins. Keep its context open through restore, SQL verification and reconciliation. It verifies the protected head, source pins, signing keys and complete chain against the live fence.
3. Restore both databases into an empty, offline replacement. Use the existing six-table authority SQL verifier. With all writers stopped, initialize a fresh correctly owned checkpoint inode with the verified bytes. Run the isolated `append_provision.py --execute --device ... --inode ... --restored-records ... --chain-sha256 ...` setter and require its exit, readback and signed-chain validation. Keep that file read-only for application and recovery roles.
4. Run the existing restore-session fence before reconciling with the dedicated recovery role. Use `recovery_driver.reconcile_exact` with the frozen chain digest and the real mail-worker lifetime lock. Verify all events, sealed fingerprints and application retirement mirrors. Keep maintenance in force for a staging manifest, stale data, wrong key, failed purge, interrupted operation or missing account history. Check ordinary startup against the repaired app and verify that unrelated data is intact.
5. Keep the station fenced while the operator verifies the replacement and confirms old writers are gone. An explicit `Witness.release` requires the exact fenced cut and a previously unused public key for the next service generation. Requalify its version-2 publisher profile and private tunnel before admitting a new writer. The public app and station listener cannot lift this fence.

The legacy app-only operator continues to cover retained-authority recovery. The independent path requires the external journal plus operator-controlled target isolation, trusted custody and backup availability. Deployment and retention must be qualified on the actual service and recovery station.
